# Aether OS — Static Architecture & Code Audit
## 2026-09-23

This audit compares the documented Aether architecture with the current `main` tree and source implementation. It intentionally separates **implemented**, **stubbed**, **unsafe**, and **not yet verified** behavior.

## Executive findings

The current tree is a useful native x86_64 laboratory kernel/userspace, but it is **not yet an implementation of the documented polymorphic capability microvisor**. The audit below records source-level gaps separately from items that have since been repaired. The largest discrepancies are architectural, not cosmetic.

### P0 — User syscall ABI is inconsistent with the Ring3 programs

`isr_syscall` saves registers in this order:
`rax, rbx, rcx, rdx, rsi, rdi, rbp, r8..r15`.

Therefore, at the handler frame:
- `[0]` = RAX
- `[4]` = RSI
- `[5]` = RDI
- `[9]` = R10
- `[10]` = R11
- `[11]` = R12
- `[14]` = RAX

But `syscall_handler` currently interprets:
- a1 = frame[9]
- a2 = frame[10]
- a3 = frame[11]

and dispatches write as `sys_write(a2, a3)`.

The bundled Ring3 programs use the conventional register arrangement RDI/RSI/RDX. Consequently the current syscall implementation does not consume the arguments those programs actually place in registers.

**Required fix:** define one Aether syscall ABI explicitly and make both `isr.s`, `handlers.rs`, and all Ring3 binaries obey it. Add an automated ABI smoke test that proves pointer/length/value round-trips.

### P0 — TSS descriptor construction is incorrect for a 64-bit TSS

The GDT contains two entries for the TSS, but `gdt.rs` writes the upper TSS base into fields of `GdtEntry` that do not represent the required 64-bit TSS high descriptor layout.

For a 64-bit TSS descriptor, the second 8-byte slot is the upper 32 bits of the base plus reserved fields. The current code places bits 40..63 into `limit_low/base_low` of the second entry, which is not the architectural encoding.

**Required fix:** introduce an explicit 16-byte TSS descriptor representation and encode base[0:32] and base[32:64] correctly. Validate with `sgdt/str` diagnostics and a CPL3->CPL0 interrupt transition test.

### P0 — Process↔Personality integration is present, but one compatibility constructor bypassed it

The current `Process` structure has an explicit `PersonalityId` owner. `create_from_image_with_personality()` stores that owner, loads the personality when needed, and attaches the process to its lifecycle count; `destroy()` detaches it. `count_by_personality()` compares the requested ID correctly.

A remaining correctness defect was found in the legacy `process::create(p, entry, stack)` helper: it accepted a personality argument but silently called `create_from_image()`, converting the requested owner to `PersonalityId::None`.

**Required fix:** route the helper through `create_from_image_with_personality()` and preserve the supplied owner. Add a regression test if this compatibility helper remains reachable.

### P0 — Capability system is only a data structure, not an access-control mechanism

`Cap` is currently just `{ id, rights }` and `CapTable` is a fixed array. There is no object table, no owner binding, no rights validation on lookup, no capability transfer/revocation model, and no syscall/resource path that requires a capability.

Therefore the documented statement “everything only through capabilities” is not true of the current implementation.

**Required fix:** introduce kernel object handles/capabilities with generation or equivalent stale-handle protection, owner/domain association, rights checks, and syscall integration before calling capability security implemented.

### P1 — ELF loader has memory-accounting and validation holes

`LoadedImage.pages` stores only 8 physical pages, while the loader can allocate more than 8 pages across PT_LOAD segments. Extra allocated pages are then not recorded for later process destruction.

The loader also accepts malformed program-header ranges more readily than a production loader should: `phoff + i*phentsize`, `vaddr + memsz`, and `p_offset + filesz` need checked arithmetic and range validation.

It does not yet enforce PT_LOAD permissions from ELF `p_flags`; all mapped pages are writable/user pages.

**Required fix:** use dynamic/bounded page ownership metadata, checked ELF ranges, canonical user virtual-address limits, overlap checks, and R/W/X permission mapping.

### P1 — User pointer validation is range-based, not page-table/capability based

`user_ok()` only checks that a pointer lies in 0x40000000..0x40010000 and length <= 4096. It does not verify that every touched page is mapped user-accessible, that the requested range belongs to the calling process, or that the operation has the required object capability.

A future process with a different valid mapping inside/outside this fixed window would not be handled correctly.

**Required fix:** centralize checked user-memory access against the current process address space and required rights.

### P1 — Scheduler is currently cooperative scaffolding, not a real scheduler

`sched::run_all()` only selects the first Ready process and enters it. `schedule()` is empty. There is no timer-driven preemption, context-switch state, blocked/wakeup model, or robust return-to-scheduler path.

**Required fix:** establish a minimal process/thread context structure, timer source, runnable queue, context switch, and explicit states.

### P1 — AetherFS comments and implementation disagree

The filesystem module is documented in parts of the project as RAM/read-only storage, while `fs.rs` contains persistent disk formatting and write paths through ATA. `format()`, `write_super()`, bitmap updates, root updates, and file writes are real disk-write operations.

This is a dangerous documentation/behavior mismatch because the project explicitly requires host-disk writes to be prohibited during the current hardware-validation stage.

**Required fix:** separate:
1. AetherFS RAM image;
2. read-only host/disk inspection;
3. an explicitly opt-in persistent AetherFS block device.

No persistent write path should be reachable from normal AH532 boot until its safety policy is explicitly defined and tested.

### P1 — AetherFS on-disk limits are internally inconsistent

`DirEntry` declares a 28-byte name, but the serialized format actually stores only 22 bytes of name plus length/flags/start/size. The code contains an abandoned first parsing pass and then a second “fixed” layout.

`MAX_FILE_SECTORS = 16` limits files to 8 KiB, while older comments still mention one-sector files.

**Required fix:** define one packed on-disk specification, remove dead parsing code, and test create/read/write/delete at boundary sizes.

### P1 — AHCI DMA addressing is limited to 32-bit physical addresses

AHCI structures and buffers are programmed with upper address dwords set to zero. This works only while allocated physical memory is below 4 GiB. The current PMM is intentionally tiny, so it is acceptable as a lab constraint, but it must be documented as such.

### P1 — PMM assumes a fixed 64 MiB usable region

`kernel_main` initializes PMM with 2 MiB..66 MiB without consuming the Multiboot memory map. This is deliberately conservative, but it means Aether is not yet a real physical-memory manager for arbitrary x86_64 hardware.

**Required fix:** consume Multiboot memory-map entries, reserve kernel/page-table/framebuffer/ACPI regions, then allocate only genuinely usable pages.

### P1 — Framebuffer mapping silently relies on identity mappings and ignores map failures

`map_fb_range()` deliberately skips mapping below 1 GiB and ignores `map_page()` failure as “may already be mapped”. This is acceptable only under the current boot identity-map assumptions; it is not a general framebuffer memory-management API.

### P1 — Intel video layer is still diagnostic, not a complete driver

The current video source correctly avoids the previously unsafe GGTT/GSM mapping, and the AH532 target is correctly identified as Sandy Bridge HD 3000 (8086:0116). However:
- BAR mapping is diagnostic;
- existing scanout attachment is conditional;
- EDID/GMBUS is explicit;
- no complete connector/power/modeset ownership exists;
- GGTT/GSM remains blocked.

The documentation must continue to label this as a staged driver, not “complete Intel graphics”.

### P1 — PS/2 mouse geometry still contains a fixed 800x600 clamp

The current `ps2.rs` shown in the repository still clamps MX/MY to 799/599. This conflicts with the earlier dynamic framebuffer fix described in project history.

**Required fix:** derive the clamp from current framebuffer dimensions, or move pointer bounds into the input/display abstraction.

### P2 — Personality modules are explicit stubs

Linux/Android/Windows modules currently expose tiny syscall switches and fake process starters. They do not implement ELF/PE loading, real ABI compatibility, Binder/ART integration, NT semantics, or native compatibility layers.

This is not a defect if clearly marked as scaffolding, but it is a direct gap versus the architecture documents.

### P2 — README status is stale and contradictory

README says “Project just created” and “architecture in design”, while `docs/STATUS.md` describes substantial working kernel/userspace and hardware evidence.

**Required fix:** make README link to the laboratory status and clearly distinguish architecture target from current implementation.

## Cross-document contradictions found

1. **“Microvisor/polymorphic kernel” vs actual implementation:** current code is a monolithic kernel with built-in desktop, storage, drivers and stub personalities.
2. **“Everything through capabilities” vs actual syscalls:** current syscalls directly access framebuffer, input and filesystem without capability checks.
3. **“Personality owns every process” vs Process:** no personality field/attachment exists.
4. **“Fully unloadable personality” vs implementation:** load/unload toggles a boolean; there is no module code/data allocation to unload.
5. **“No host storage writes” vs AetherFS:** persistent write functions exist in the kernel.
6. **README “project just created” vs STATUS:** README is outdated.
7. **Dynamic mouse geometry claim vs current PS/2 clamp:** source still contains fixed 800x600 bounds.
8. **“QEMU smoke proof” vs syscall ABI:** QEMU can prove that CPL3 reached `int 0x80`, but does not by itself prove correct syscall argument semantics.

## Recommended repair order

1. Fix syscall ABI and add an ABI regression test.
2. Fix TSS descriptor encoding and prove CPL3 interrupt/syscall entry.
3. Make Process↔Personality ownership real.
4. Implement actual capability lookup/rights checks.
5. Harden ELF loader and page ownership.
6. Separate RAM AetherFS from persistent disk writes.
7. Fix PMM to consume the Multiboot memory map.
8. Replace fixed PS/2 pointer bounds.
9. Update README/STATUS terminology.
10. Only then expand scheduler, personalities, and active Intel modesetting.

## Evidence policy

A source-level finding is classified as a defect or architectural gap even when the current boot image happens to work. Runtime evidence can downgrade or upgrade the severity of a finding, but must not be replaced by a build-success claim.

The AH532 remains the hardware authority for Sandy Bridge Gen6 display behavior. QEMU evidence remains useful for deterministic kernel/userspace tests but is not evidence of AH532 hardware correctness.

### Capability authority hardening — 2026-09-24
- Request: continue the P0 capability work after the Process↔Personality repair; every substantive Aether action remains logged.
- Source review confirmed the previous capability table was slot-based: revoke cleared a slot, but a later insert could reuse that slot, so a previously issued numeric slot could become ambiguous/stale.
- Repair: external capability handles now carry a generation tag in kernel/src/capability/mod.rs. Revoke advances the slot generation; lookup/check/revoke reject stale generations. A deterministic self-test now proves revoke -> reuse produces a different handle and the old handle remains denied.
- The existing bootstrap process ABI intentionally keeps fixed slots 0/1/2 for READ/WRITE/MAP. Syscall checks were switched to an explicit check_slot() path so the new external-handle encoding does not silently break the current bootstrap ABI.
- This does NOT complete the documented capability microvisor: there is still no global object registry/authority domain, capability transfer/grant protocol, or universal capability-mediated resource model.
- Validation requirement: GitHub build/CI must pass before treating the source change as build-verified; no runtime AH532 claim is made here.
